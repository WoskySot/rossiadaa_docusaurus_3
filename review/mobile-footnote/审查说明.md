## 二、第一轮：必须修的缺陷（已修复）

### 现象

真机/触屏模拟下，**每一条注解的原文都被直接铺进了正文**——段落变长、列表项里混进整句释义。
桌面端窗口缩到 390px 宽也**完全看不出来**，只有设备真正报告"无悬停、粗指针"时才暴露。

### 根因

`src/css/custom.css` 当初把 `.fnPop` 的**全部**声明都写进了同一个媒体查询：

```css
@media (hover: hover) and (pointer: fine) {
  .fnRef { position: relative; display: inline-block; }
  .fnPop {
    position: absolute;          /* ← 也在这里 */
    visibility: hidden;          /* ← 也在这里 */
    opacity: 0;                  /* ← 也在这里 */
    ...
  }
}
```

手机匹配不到这个查询 ⇒ **这条规则整体不生效** ⇒ `.fnPop` 退回 `<span>` 的天性：
`position: static`、`display: inline`、`visibility: visible`、`opacity: 1`。
而它的内容正是插件从文末复制来的注解原文，于是整段文字以普通行内文本的身份留在了正文里。

一句话：**"藏起来"这件事不该由媒体查询决定。**

### 修复

拆成两层——基础层无条件藏，指针层再放回来：

```css
/* 基础层：不设媒体查询，任何环境都成立 */
.fnPop { display: none; }

@media (hover: hover) and (pointer: fine) {
  .fnPop { display: block; position: absolute; /* … */ }
  .fnRef:hover > .fnPop, .fnRef:focus-within > .fnPop { visibility: visible; opacity: 1; }
}
```

用 `display: none` 而不是 `visibility: hidden`：前者把元素彻底移出布局，连"绝对定位元素仍会撑大可滚动区域"
这种边角情况都一并避免。副作用是好的——触屏与读屏软件都不会再读到重复的注解文本。

### 量化影响

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| `.fnPop` 计算样式（触屏） | `display:inline` / `position:static` / `visibility:visible` / `opacity:1` | `display:none` |
| `.fnPop` 盒子尺寸（触屏） | 343.8×72.8（在流内） | 0×0（不在流内） |
| 首段高度（390×844） | 161.7px | 108.9px（本轮复测 135.3px，取决于测的是哪一段） |
| 受影响的引用 | 整页 10 条注解，每一处 | 0 |
| 桌面端弹窗 | 448×66.5px 悬停预览 | 不变 |

## 三、第二轮：触屏改成"点一下弹窗、再点一下跳转"

### 为什么要改

第一轮把触屏的弹窗关掉之后，触屏用户**看不到注解内容本身**——点编号就直接被送到文末，
只能顺着文末条目读，读完再自己滚回来。手机上"悬停"这个动作确实不存在，但"先看一眼、想细看再过去"
这个需求是存在的。于是把两段式点击补上：**第一下给内容，第二下给跳转。**

### 交互规则

| 动作 | 触屏 | 指针设备（桌面） |
| --- | --- | --- |
| 点/悬停正文编号 | 第 1 下：弹出该编号的注解弹窗，**不跳转、不改地址栏** | 悬停：弹出弹窗 |
| 弹窗已显示时再点同一条编号 | 第 2 下：收起弹窗并跳到文末条目（居中 + 1.6s 高亮） | 单击：直接跳到文末条目 |
| 点另一条编号 | 换成那一条的弹窗（不跳转） | — |
| 点弹窗内部空白 / 点正文别处 / 滚动 / `Esc` | 收起 | 移开鼠标即收起 |
| 点文末条目尾部的 `↩` | 跳回正文编号（居中 + 高亮） | 同 |

键盘与辅助技术激活（合成点击，`detail === 0`）**不适用两段式**——直接跳转，否则键盘读者要按两下。

### 弹窗落位的四条规则

1. **优先弹在编号上方**；上方空间不够就**翻到下方**（小三角同时翻面）。
2. 左右**贴边时整块平移**回视口内（三角跟着移到仍指向编号的位置）。
3. 视口极矮时按"编号那一侧剩余空间"**限高**，超出部分**弹窗内部滚动**（此时小三角让位隐藏）。
4. 以上任何情况下**不出视口、且不盖住编号**——盖住编号第二下就点不到它了。

### 实现要点（写给维护者）

- **门控写在设备的输入方式上，不是视口宽度上**。`(hover: hover) and (pointer: fine)` 命中即整个触屏模块
  **直接不安装**，所以桌面端一行代码都没被走到。把窗口拖窄到 390px **不会**触发触屏分支——这点和第一轮的
  缺陷同源：媒体查询描述的是输入设备，不是窗口大小。
- **监听器挂在捕获阶段**（`document.addEventListener('click', onClick, true)`），触屏模块先吃掉第一下，
  再让冒泡阶段负责跳转的模块看到 `event.defaultPrevented` 而主动让路。顺序反了就会出现"弹窗开了又立刻跳走"。
- **编号的点击热区**在触屏上撑到 `padding:.5rem .35rem` 并配等量负外边距（`margin:0 -.35rem`），
  只扩大命中范围、不动行盒高度。热区**必须做在 `<a>` 自己身上**：早先用绝对定位伪元素时，
  伪元素盖在 `<a>` 之上，第二下的命中目标变成了外层 `.fnRef`（不是链接），跳转分支拿不到 `<a>` 就静默放弃了。
- 跳转模块里补了 `resolveAnchor()`：即使命中目标确实是外层 `.fnRef`，也能从容器里把那个 `#` 链接捞回来。
  两道保险都留着，热区算法将来再改也不会退化成"弹窗关掉了却没跳转"。
- 弹窗状态放在 `data-fn-*` 属性上（`data-fn-open` / `data-fn-flip` / `data-fn-scroll`），
  几何量走 CSS 变量（`--fn-pop-shift` / `--fn-pop-max`），样式与逻辑各管一摊。
- `<a>` 被点后的原生导航由 `preventDefault()` 接管，跳转与高亮由
  `src/clientModules/footnoteScrollCenter.js` 统一完成（见下一节）。

## 六、已知限制（非缺陷，供权衡）

1. **平板外接键鼠**：`(pointer: fine)` 由主指针决定，iPad 接键盘/触控板仍可能报 `coarse`，
   此时 Tab 聚焦也不会弹出弹窗。若要"外接键鼠也能用弹窗"，把门控放宽为 `@media (hover: hover)`
   （去掉 `pointer: fine`）即可——代价是某些混合设备上可能弹出后无法收起。**本版暂不处理。**
2. **文档首屏上方的落点**：受页面边界限制无法居中，属几何必然。
3. 弹窗副本仍留在 DOM 里（`display:none`），不参与布局、不进可访问性树。

# 追加：非移动端也用上同一套弹窗定位（2026-09-17）

前两轮里"弹窗自己找位置"只在触屏生效，指针设备一直靠 CSS 静态定位（往上弹、居中于编号），
于是窄窗口、贴近页首页尾、长注解这些情况下会探出视口或被裁掉。本轮把算法抽出来给两边共用。

## 一、实现

| 文件 | 角色 |
| --- | --- |
| `src/clientModules/footnotePopoverFit.js` | **新增**。两个平台共用的四步算法：量内容真实高度 → 定竖直方向与高度上限 → 定水平平移 → 判断是否需要内部滚动。只写 `--fn-pop-max` / `--fn-pop-shift` 与 `data-fn-flip` / `data-fn-scroll`，几何留在 CSS |
| `src/clientModules/footnoteTouchPopover.js` | 改为引用共用算法，本模块只剩"开与关" |
| `src/clientModules/footnotePopoverHover.js` | **新增**。指针设备侧：`pointerover` / `focusin` 时套用算法，**不改变可见性**（显示仍由 `:hover` / `:focus-within` 决定） |
| `src/css/custom.css` | `[data-fn-scroll]` 去掉触屏专属的 `[data-fn-open]` 前缀；**删除 `@media (max-width:996px)` 的"窄窗口向左展开"分支** |

删那条窄窗口分支的理由：它的 `transform` 不含 `--fn-pop-shift`，会**绕开平移量**，
窄窗口里贴边平移会直接失效；而且它是只属于桌面的第二套几何，与"两边一致"冲突。
贴边问题现在统一由平移量解决（实测 480px 宽下 10 个编号全在视口内）。

> 这一节原来写的是给改代码的人看的说法。下面换成日常话，每条讲清三件事：
> **什么情况下会碰到 → 会坏成什么样 → 要不要紧**。
> 三条都只跟"点编号时冒出来的那个小气泡"有关：正文阅读、点编号跳到文末、点文末 `↩` 跳回来、
> 搜索等等都不受牵连。而且这三种情况**都不会报错、不会白屏**，最多是气泡的位置或显示不对——
> 正因为它不吭声，才需要单独提醒。技术细节仍留在代码注释与 `04-footnote-guide.mdx` 里。

### 第 1 条：还没露面的气泡，量不出个头

**什么时候会碰到**：只有当你去改"气泡打开时先量一下它多大"这段代码时才会碰到。平时浏览网页，手机也好电脑也好，都不会碰到。

**为什么容易出错**：浏览器有个规矩——一个被藏起来的东西，问它"你多宽、多高"，它一律回答 0。
麻烦的不是这个 0，而是程序会拿它去算，算出"这个气泡很小、上面完全放得下"，
于是既不把它翻到下方，也不给它封顶，任由它往上顶。

**坏了是什么样**：气泡探到屏幕外面，或者贴着屏幕上沿被切掉一截，后面的注解内容看不到。
它**不会报错、不会白屏**，看上去一切正常，只是位置不对。

**现在要不要紧**：不要紧。现在的写法是——量之前如果发现气泡还藏着，就先临时显示一下，量完再藏回去，所以量到的始终是真实尺寸。这条只是提醒：**以后别把这个"先显示再量"的动作删掉**。

### 第 2 条：要用"会往上传递"的鼠标事件，别换成"只在原地响"的

**什么时候会碰到**：改"鼠标移进气泡 / 移出气泡"那段监听的时候。

**为什么要这么选**：一页里有十几条脚注，希望只在一个地方写一套监听就照看全部，不必每条都单独挂一份。
能这么做的前提是：事件会一层层往上传递（`pointerover` / `pointerout` 就是这种）。
另两个名字很像的事件（`pointerenter` / `pointerleave`）只在原地响、不往上传递，挂在页面根部一条消息都收不到。

**坏了是什么样**：全站脚注的悬停气泡集体失灵（鼠标放上去没反应），或者只有个别几条还有反应。

**还有半句**：光知道"有东西进来了"不够，还得看**是从哪儿进来的**。鼠标在气泡内部从一个字挪到另一个字，同样会触发一次"进来"。不看来源就会来回误判，气泡一闪一闪。

**现在要不要紧**：不要紧，现在用的就是对的那种。

### 第 3 条：鼠标一走，上次留下的"临时设置"要擦干净

**什么时候会碰到**：改"鼠标移开时收尾"那几行的时候；或者有人觉得那两行"清理"是多余的、顺手删掉。

**为什么会出错**：注解太长、一屏放不下时，程序会给气泡临时设一个"最高只能这么高"的上限，让它自己在里面滚动。
这个上限如果没擦掉，会留到下一次。下一次打开一条**短**注解时，程序先按上次的上限把它压一道，再去量高度——
量到的是"被压过的高度"而不是真实高度，于是算错，误判成"上面放得下"，其实放不下。

**坏了是什么样**：先悬停看了一条很长的注解（气泡里出现了滚动条），移开鼠标；紧接着看附近一条同样靠近屏幕上沿的短注解——这条气泡可能被顶出屏幕上沿，或者被压成扁扁一条。**顺序换一下（比如先看短的）就正常**，所以表现像是"时好时坏"。

**现在要不要紧**：不要紧，现在鼠标移开时会把包括那个上限在内的东西一并清掉。而且就算真漏了，**按一下刷新就恢复正常**，不会一直坏、不影响别人、也不影响别的页面。这条提醒分量最轻，却最难自己察觉。

### 三条的共同点

- 触发条件都是"改代码"，不是"用网页"——**普通读者和访客不会遇到**；这类问题也不影响正文阅读、不影响点编号跳到文末、不影响点 `↩` 跳回正文、不影响搜索。
- 三种情况都**不报错、不白屏**，最多是气泡的位置或显示不对。这是单独列出来提醒的原因。
- 前两条改坏了会稳定复现（每次都错），第三条只在特定先后顺序下偶发、刷新即可消失。
