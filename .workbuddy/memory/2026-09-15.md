### 核心算法（本功能的全部难点）
行号必须**在浏览器里实测**，构建期不可能知道一行文字折成几行。做法：
1. `TreeWalker` 遍历文本节点，`Range.selectNodeContents` + `getClientRects()` 拿每个**视觉行**的矩形；
2. 聚类成行盒：与上一行盒比较，**垂直重叠 ≥ 较矮者高度的一半**才算同一行。
   用重叠法而不是"中心点距离"是必须的——`<sup>`、行内 `<code>`、加粗等会产出比正文行更高/更偏的矩形，
   中心点法会把它们误判成独立行；重叠法能正确合并，同时不会把相邻两行黏起来；
3. 行盒按上边排序后**顺序编号**（排序稳定性的来源），`mark = start + 行号 - 1`，只在 `行号 % step === 0` 时渲染；
4. 边码 `top` 用行盒**垂直中心**，CSS 里 `transform: translateY(-50%)` 让数字与文字基线视觉齐平。

### 关键设计决定
- **`display:none` 不能靠 getComputedStyle 判**：被隐藏祖先包住的元素 computed display 仍是自己的值。
  正解是"**拿不到 rect 就不算一行**"——`Range.getClientRects()` 对隐藏内容天然返回空列表，还省掉大量样式计算。
- **SSR 首屏渲染空边码栏**（`useState([])`，测量放 `useEffect`），版心白边由 CSS 无条件预留，所以数字"迟到"不引起布局跳动。
  符合官方 SSG 文档"首次客户端渲染必须与 SSR 产物一致"的要求。
- **MutationObserver 只观察内容容器，不观察包着边码栏的外层**，否则渲染数字会触发观察器形成死循环。
  同理 `isIgnored` 里用 `closest('[data-bianma-gutter]')` 跳过边码栏自己（也顺带跳过嵌套的内层栏）。
- **窄屏用 `min()` 而不是变量覆盖**：`gutter` 由组件以内联自定义属性下发，内联优先级高于媒体查询，
  在 `@media` 里改写 `--bianma-gutter` 会失效。正解是媒体查询里直接 `width/padding: min(var(--bianma-gutter), 36px)`。
- **对比度实测**（12px 属"正常字号"，WCAG AA 需 4.5:1）：
  亮色 emphasis-500 `#bec3c9` → 1.8:1 ✗；-600 `#8d949e` → 3.1:1 ✗；-700 `#606770` → 5.7:1 ✓。
  暗色底 `#1b1b1d` 上 emphasis-400 `#8d949e` → 5.6:1 ✓。最终取 light -700 / dark -400。
- **wrap 而非 eject** 两处主题文件都要显式说明：`.markdown` 是原组件的子元素，我们只在外面加父级，
  所以 Infima 的直接子代选择器（`.markdown > h2`、`.markdown > *:last-child`）不受影响（已核对产物 DOM）。
- **没写 `bianma` 的页面返回的 DOM 与装这个功能之前完全一致**（不会多出一层 div）——`normalizeBianmaOptions` 返回 null 时直接走原组件。
- front matter 自定义键能存活，是因为 `DocFrontMatterSchema` 带 `.unknown()`（已核对源码）。

### 踩坑（都是真踩出来的）
1. **锚点自己那份隐藏文本会污染测量**：锚点内有 `font-size:0` 的文本子节点，
   `TreeWalker.nextNode()` 从锚点出发会**先返回它自己**，其矩形零宽 → 落点判断退化；
   段首锚点因此退化成"用整段 `<p>` 的矩形定位"，实测偏差 26–46px。
   正解：walker 过滤器里同时排除 `parent.closest('[data-bianma-mark]')`。
2. **落点规则要先判"锚点前是否还有本段文字"**：`anchor.parentElement.contains(prevChar.node)` 太脆
   （锚点常写在 `<a>/<strong>` 内部）；正解是往上找最近的**非行内** display 祖先再 `contains()`。
   规则：段中 → 前一个字符所在行；段首 → 后一个字符所在行（即该段第一行）。
3. **MDX 里裸写 `<span …>` 会被当 JSX 吃掉**：文档少一段文字、还凭空多出一个空锚点（白边里冒出"文本"两字）。
   要展示标签必须包反引号。本项目第二个同类坑（第一个是 `{`）。
4. **校验正则别用 CSS Module 类名**：产物里是 `.rule_T_Uk`、`.mark_DHNO` 这类哈希名，`/\.rule\{/` 永不命中；
   改判 minified 子串（如 `--bianma-rule-color);inline-size:1px;position:absolute`）。
5. **亮色下 html/body 都没有显式背景**：页码压在浏览器画布默认白上，探针 walk-up 找不到不透明背景 →
   对比度算不出来；兜底取 `#ffffff`（暗色 `#1b1b1d`）。
6. 细线配色：亮色 `emphasis-200` 几乎与纸同色（截图里基本看不见）→ 改 `emphasis-300`（1.8:1，装饰但看得见）。

### 关键坑与技术决定
1. **不能用 `scroll-margin-top: calc(50dvh - .5em)` 代替 JS**：`scroll-margin` 作用在元素自身几何上，
   之后任何一次 `scrollIntoView` / Tab 聚焦 / 片段导航都会带上它，等于顺手改坏别处的滚动。
2. **居中要选 `.fnRef`，不能选 href 指向的那个 `<a>`**：Docusaurus 通过 `MDXComponents/A` 的
   `useAnchorTargetClassName`（`@docusaurus/theme-common/lib/utils/anchorUtils`）给带 `id` 的锚点目标加了
   `class="anchorTargetStickyNavbar_*"` → `scroll-margin-top: calc(3.75rem + .5rem)`，
   而 `block:'center'` 会把这段边距算进"对齐区域"，落点整体下移约 34px。`.fnRef` 是插件自造容器、无边距。
   （实测：选 `.fnRef` 时 boxCenter 与视口中心偏差 ±0.5px；同时 `<a>` 的中心天生比它高约 4.3px。）
3. **判定返回箭头的两种信号都收**：`a[data-footnote-backref]` 属性 + href 形状 `^(?:user-content-)?fnref-`，
   抗上游改名（GFM 同时会加 `class="data-footnote-backref"`，那是类名不是属性，不能只认它）。
4. **刻意不碰 history**：实测仅 `history.pushState` 改 hash 时，路由层**不会**跟着滚
   （`ClientLifecyclesDispatcher.scrollAfterNavigation` 未触发，页面停在原处）——所以"改 hash 会打架"
   这个最初假设是错的，代码注释已按实测改写。仍选择不动 URL：不与路由层内部行为耦合
   （将来任何版本补上"hash 变化即滚动"都会用顶格对齐覆盖居中）。代价只是地址栏停在 `#user-content-fn-N`。
5. **`prefers-reduced-motion` 要手动读**：`scrollIntoView({behavior:'smooth'})` 不保证遵守系统偏好，
   所以 `matchMedia` 命中时改用 `'auto'`。
6. **点击目标被吸顶导航栏挡住**：验收脚本第一版把页面滚到最底再按坐标点，`elementFromPoint` 命中的是导航栏
   （链接恰好落在视口顶部 0–60px 内）→ 改成先把待点链接 `scrollIntoView({block:'center'})` 再点，
   并断言 `elementFromPoint` 落在链接内，否则直接报错而不是静默失败。
7. **`Page.captureScreenshot` 的 `clip` 用文档坐标**，不是视口坐标；直接用 `getBoundingClientRect()` 会截出白图。
8. 聚焦落点会让 `.fnRef:focus-within` 的弹窗重新出现——这与浏览器原生片段导航的行为一致（原生也会聚焦目标），
   不是新引入的，所以保留。

### 核心决定：放弃 `scrollIntoView`，自己算 scrollTop
关键新事实：**文末 `<li id="user-content-fn-1">` 也带 `anchorTargetStickyNavbar_*`**（结构体检确认
`liClass: "anchorTargetStickyNavbar_Vzrq"`，而它的祖先链上没有任何可滚动容器，`overflow-y` 全是 `visible`）。
`scrollIntoView({block:'center'})` 会把元素自身的 `scroll-margin`（3.75rem+.5rem）算进"对齐区域"，
居中点因此下移约半个边距。所以这一版自己算几何，`scroll-margin` 一概不参与，顺便换来三处想要的自由度：

1. **找滚动容器**：从内往外找最近的 `overflow-y: auto|scroll|overlay` 且 `scrollHeight > clientHeight` 的祖先，
   找不到就用 `document.scrollingElement`。**刻意不认 `overflow: hidden`** ——
   页面里存在用 hidden 裁剪溢出内容的盒子（弹窗就靠它裁），把它当容器会让坐标系算错。
   走链时一旦遇到 html/body 立刻停（`overflow-x: hidden` + `overflow-y: visible` 会让 computed `overflow-y`
   变 `auto`，body 会被误判成滚动容器）。
2. **坐标系**：`元素在内容里的位置 = rect.top - 滚动视口顶 + scroller.scrollTop`；
   文档滚动时视口顶记 0（`documentElement.getBoundingClientRect().top` 等于 `-scrollTop`，不能用）。
   视口高一律用 `clientHeight`（它才是 `scrollHeight` 的参照系）。再夹进 `[0, scrollHeight - clientHeight]`。
3. **遮挡与超高**：把结果夹进"完整可见"区间 `[元素底+24-视口高, 元素顶-吸顶导航栏高-8]`。
   导航栏高度**实时量**且只在它确实 `fixed/sticky` 且贴着顶部时才算（`hideOnScroll` 把它移出视口时不留边距）。
   放得下时这段夹取是空操作（居中的结果本来就在区间内），只在页尾/超高元素时才生效；
   元素比可用高度还高（移动端长注解）→ 退回"开头对齐到导航栏下方"，保证从第一行可读。

### 另外三处细节
- **滚动结束后校正一次**（`scrollend`，不支持的浏览器 500ms 兜底）：移动端地址栏在平滑滚动中收放会改变
  视口高度，落点可能偏掉几十像素；偏差 > 2px 就静默用 `instant` 纠一次。两道保险防止"把读者自己滚到的
  位置纠回来"：900ms 时限 + 焦点已不在落点上就放弃。
- **`behavior: 'auto'` 不等于即时**：若将来给 html 加 `scroll-behavior: smooth`，`auto` 会变成平滑滚动
  （规范如此），所以减少动效时显式传 `'instant'`，并在 `catch` 里退回 `scrollTo(0, top)` / `scrollTop =`。
- **焦点要自己补，但不能乱加 `tabindex`**：`preventDefault` 之后原生"顺序焦点导航起点"不会自动挪。
  正解是只给**非天生可聚焦**的元素补 `tabindex="-1"`（用 `NATURALLY_FOCUSABLE` 选择器判定），
  否则会给正文那个 `<a href>` 也加上、把它从 Tab 顺序里踢出去。实测确认 `<a>` 未被加（`anchorTabindex: null`、
  `anchorInTabOrder: true`）。
  附带发现：点过普通页内链接后 React 重渲染会抹掉 `<li>` 上后加的 `tabindex`——**无害**（每次跳转都会重加），
  但别指望它长期存在。

### ⚠️ 新踩的坑（很值得记）：`Page.captureScreenshot` 默认 `captureBeyondViewport: true`

正解：截图一律显式传 `captureBeyondViewport: false`（顺带：`clip` 用**文档坐标**，与前一节第 7 条一致）。

标线是渲染的一部分，比按缩放比例目测像素可靠得多。本轮两条标线完全重合，证明落点确实居中。

## 审查移动端脚注表现 → 发现并修掉一个只在真机暴露的严重缺陷（同日晚）

用户要求"审查弹出窗口式脚注在移动端的实现状况"，并要 GIF / 效果图。
审查用的设备模拟是 `mobile:true` + `Input.dispatchTouchEvent`（真实触摸事件，不是 `element.click()`），
此时 `matchMedia('(hover: hover)')=false`、`(pointer: fine)=false`、`(pointer: coarse)=true`，与真机一致。

### 🚨 缺陷：`.fnPop` 的"藏起来"写在了媒体查询里面

`src/css/custom.css` 里，`.fnRef` 与 `.fnPop` 的**全部声明**（含 `position:absolute` / `visibility:hidden` /
`opacity:0`）都关在 `@media (hover: hover) and (pointer: fine)` 内。手机匹配不到该查询 ⇒ 整条规则不生效 ⇒
`.fnPop` 退回 `<span>` 的天性（`position:static` / `display:inline` / `visibility:visible` / `opacity:1`）
⇒ **插件复制到编号旁的注解原文以普通行内文本的身份留在正文里**。
桌面端窗口缩到 390px 也完全看不出来，只有设备真报"无悬停"时才暴露。

实测（390×844，触屏）：
| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| `.fnPop` 计算样式 | `display:inline` / `position:static` / `visibility:visible` / `opacity:1` | `display:none` |
| `.fnPop` 盒子 | 343.8×72.8（**在流内**） | 0×0（不在流内） |
| 首段高度 | 161.7px | 108.9px |
| 受影响引用 | 整页 10 条注解每一处 | 0 |

### 修复：拆成"基础层 + 指针层"

```css
/* 基础层：不设媒体查询，无条件成立 */
.fnPop { display: none; }

@media (hover: hover) and (pointer: fine) {
  .fnPop { display: block; position: absolute; /* …其余不变 */ }
  .fnRef:hover > .fnPop, .fnRef:focus-within > .fnPop { visibility: visible; opacity: 1; }
}
```
- 用 `display:none` 而非 `visibility:hidden`：彻底移出布局，连"绝对定位元素仍会撑大可滚动区域"的边角情况
  都避免；副作用是好的——触屏与读屏软件都不会再读到重复注解。
- 桌面端回归：1440×900 与 900×700（≤996px 左展开分支）× 明暗，悬停后均 `display:block / visible / op=1`、
  448×66.5px、视口内，未被改坏。
- 文档同步：`04-footnote-guide.mdx` 维护者小节补了这条坑（"藏起来必须写在媒体查询之外"）。

### 教训（泛化）
**凡是用来兜底的属性（把元素藏起来、把页面降级），必须写在媒体查询之外。**
把"隐藏"和"交互能力"写在同一个 `@media` 里，会让"查询不匹配"从"功能不可用"升级成"页面渲染错乱"。
验收时不能只看桌面窗口缩放——`hover`/`pointer` 媒体特性跟**输入设备**绑定，跟**视口宽度**无关，
必须用 `mobile:true` + `touch` 模拟或真机才能暴露。已写进 MEMORY.md。

## 第二轮：触屏改成"点一下弹窗、再点一下跳转"

### 需求
触屏上正文注释编号也要能看注解内容：第一下弹出该编号的弹窗，弹窗已显示时再点一下才执行跳转；
指针设备（桌面）的体验不能被影响。

### 实现
- 新增 `src/clientModules/footnoteTouchPopover.js`：门控 `(hover: hover) and (pointer: fine)`，
  命中即**整个模块不安装**（桌面连监听都没有）。监听挂**捕获阶段**，忽略 `defaultPrevented` /
  非左键 / 修饰键 / `detail===0`（键盘与辅助技术直接放行跳转，不要求点两下）。
- 状态用 `data-fn-open`（+ `data-fn-flip` 翻到下方 / `data-fn-scroll` 限高内部滚动）表达；
  几何量走 CSS 变量 `--fn-pop-shift`（贴边平移）/ `--fn-pop-max`（限高）。
- 落位优先级：**上方 → 下方 → 水平平移 → 限高 + 内部滚动**；任何情况不出视口、且不盖住编号。
- 触屏热区做在 `<a>` 自己的 padding（`.5rem .35rem`）上 + 等量负 margin。
- `footnoteScrollCenter.js` 加 `resolveAnchor()`：命中目标落到外层 `.fnRef` 时也能捞回 `#` 链接。
- `src/theme/Root.js` 同时安装两个 clientModule。

### 踩到的坑
- **伪元素热区会顶掉链接**：`.fnRef::before{position:absolute; inset:-.5rem -.3rem}` 盖在 `<a>` 之上，
  第二下命中目标变成外层 `.fnRef`，`closest('a[href]')` 拿到 null → **弹窗关了却不跳转**。
  改成 padding 热区 + `resolveAnchor()` 双保险。
- **无头 screencast 是"变化驱动"的**：页面静止时几乎不产帧——"弹窗停留 1.8s"整段只录到 **1 帧**，
  而滚动动画段是 ~17–25ms/帧。于是**用时间去反推帧序号必然错位**，一度裁出"弹窗压根没弹出来"的假象
  （实际弹窗好得很，31/31 全过）。
- **`delays` 的 50ms 下限会把时间轴拉长约 1.6 倍**（上一轮已记过，这次又踩）。根治：
  `mark()` 同时记 `frameIdx: frames.length` 当锚点，另存 `times.json`（每帧真实墙钟）。
- 合成 GIF 要按**分镜**组织：静止状态重复同一帧撑停留，动画段按目标 fps 抽帧。
- 涟漪改用**后期叠加**（`magick -draw "circle"`，半径 11→17→24 递增，叠在每次点击前 3 帧），
  页面文件与 DOM 都不动；⚠️ 坐标必须取**点击前那一帧**的视口坐标（滚动前 `getBoundingClientRect()`），
  滚动后再取会画到别处。缓存文件名要带 theme 前缀，否则暗色会复用亮色的涟漪图。
- ④的停留帧改用"scrollY 连续 3 次不变"判定出的 `landed-1` + 2 帧——正好落在"已居中 +
  1.6s 高亮仍明显"的状态；原先取 `tap-3 − 650ms` 时高亮已经快褪完了。

## 排查：改文档后缀名后 `Cannot find module '@site/docs/…' for matched aliased key '@site'`

### 现象
用户在 dev server 运行期间把 `docs/completed/01-about.mdx` 改名，浏览器/终端出现
`× Cannot find module '@site/docs/completed/01-about.md' for matched aliased key '@site'`。

### 排查过程（结论都来自实验，不靠推测）
1. 全仓搜 `01-about`：只有 `docs/hidden-pages.mdx` 的一个代码块里提到，**没有任何链接/import 引用它**
   → 排除"悬空链接"这条常见解释。
2. 翻 `.docusaurus/`：`docusaurus-plugin-content-docs/default/` 里**两份元数据并存**——
   `site-docs-completed-01-about-md-87e.json`（`source: "@site/docs/completed/01-about.md"`）
   与 `...-mdx-f67.json`（`source: "...01-about.mdx"`），**id 与 permalink 完全相同**。
   文件名里的 `87e`/`f67` 是 `docuHash(doc.source)`，所以改一次名就多一份、旧的不清。
3. 读 Docusaurus 源码 `plugin-content-docs/lib/routes.js:41-62`：
   `createData(`${docuHash(doc.source)}.json`)` + `modules: {content: doc.source}` —— 
   **路由的模块请求就是 `doc.source` 这份 `@site/...` 别名路径的原文**，写进 `.docusaurus/registry.js`。
4. 对照实验（生产构建）：`.mdx` → `.md` → 改回 `.mdx`，三次 `docusaurus build` **全部成功**，
   说明 `build` 每次重扫 `docs/`、不受影响。
5. 对照实验（dev server）：起 `docusaurus start`，**运行中**改名 →
   - 改成 `.md`：报 `Cannot find module '@site/docs/completed/01-about.mdx'`（旧名）
   - 改回 `.mdx`：报 `Cannot find module '@site/docs/completed/01-about.md'`（旧名）← 与用户报错一字不差
   ⇒ **两个方向都复现**，报错里的扩展名只是"残留的那一份"，与 `.md`/`.mdx` 谁对谁错无关。
6. 收尾验证：文件还原后（sha 一致）**全新启动 dev server → `compiled successfully`**，
   即当前磁盘状态健康，改完名重启即可，本次连 `clear` 都没用到。

### 关键事实
- 打包器是 **rspack**（`future.v4: true` + 依赖里有 `@docusaurus/faster 3.10.2`；
  dev 日志 `client (Rspack 1.7.12) compiled successfully`）。所以措辞是
  "for matched aliased key '@site'"，不是 webpack 的 "Can't resolve … in …"。查错时别被措辞带偏。
- dev 日志还出现 `persistent cache save failed … 拒绝访问 (os error 5)`（rspack 在 Windows 上
  删 `.cache/rspack/.temp/<hash>` 被锁）→ 持久化缓存可能没存下来，这解释了"为什么有时候重启也不灵、
  必须 `npm run clear`"。

### 结论与做法
- **改 `docs/` 里的文件名，先停 dev server，改完再启动。** 这是唯一需要养成的习惯。
- 重启仍报错 → `npm run clear`（删 `.docusaurus/` + `node_modules/.cache/`）再 `npm start`。
- 已写进 MEMORY.md「约定与注意事项」。
